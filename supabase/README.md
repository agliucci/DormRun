# Runner – Supabase backend

```
supabase/
├── config.toml
├── migrations/…                          # schema, RLS, payments columns
├── ONE_SHOT_ORDERS_PAYMENTS.sql          # paste in SQL editor for live orders + Stripe cols
├── seed.sql
└── functions/
    ├── transition-order/
    ├── create-payment-intent/
    ├── create-connect-account-link/
    ├── create-cash-out/                  # Transfer available balance → runner bank
    └── stripe-webhook/                   # PaymentIntent confirm / fail / refund
```

## Local development

Requires the [Supabase CLI](https://supabase.com/docs/guides/cli) and Docker.

```bash
supabase start
supabase db reset        # applies migrations/ then seed.sql
supabase functions serve transition-order
```

## Hosted project

```bash
supabase link --project-ref <your-project-ref>
supabase db push                                   # apply migrations
psql "$DATABASE_URL" -f supabase/seed.sql          # seed (idempotent, fixed UUIDs)
supabase functions deploy transition-order create-payment-intent create-connect-account-link create-cash-out
supabase functions deploy stripe-webhook --no-verify-jwt
# Also run ONE_SHOT_ORDERS_PAYMENTS.sql (or db push) before two-phone live orders.
```

## Order lifecycle

`placed → accepted → at_pickup → picked_up → en_route → delivered`

- `cancelled` is allowed from `placed` (customer) or by the system (any non-final state).
- `delivered` requires the 4-digit handoff code the customer sees.
- Call `transition_order_status(p_order_id, p_new_status, p_actor_id, p_handoff_code)`
  (or the `transition-order` edge function). With a user JWT, `p_actor_id` must equal `auth.uid()`.
  Orders have no client UPDATE policy; this function is the only write path.

## Notes for the iOS client

- **`orders.handoff_code` is not readable directly** (so runners can't see it). The customer fetches it via
  `rpc('get_handoff_code', { p_order_id })`. Because of column-level grants, select explicit columns on
  `orders` rather than `select('*')`.
- Orders are inserted as the customer (`customer_id = auth.uid()`, status `placed`); `handoff_code` is generated by default.
- `profiles` rows are created automatically on signup, with `campus_id` matched from the email domain
  (`campuses.edu_email_domains`). Enforce `.edu` requirements in the client/auth hooks if desired.
- `profiles.rating` is maintained by trigger from `ratings`.

## Stale order timeout

`cancel_stale_orders()` cancels `placed` orders with no runner after 20 minutes (service role only).
Schedule it with pg_cron (enable the extension in the dashboard first):

```sql
select cron.schedule('cancel-stale-orders', '* * * * *', $$ select public.cancel_stale_orders(); $$);
```

## Seed data

All seed rows use fixed UUIDs (prefixes `a` campus, `b` buildings, `d` dining, `c` categories, `e` items),
so re-running the seed upserts rather than duplicates. Coordinates, hours, and menus are approximate
placeholders, not official UMass Dining data.
